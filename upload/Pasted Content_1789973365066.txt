بله. این بار بر اساس **خود سورس پروژه‌ای که فرستادی** بررسی کردم، نه فقط Worklog.
و اگر OTP و درگاه بانکی را کنار بگذاریم، هنوز چند دسته تغییر مهم لازم است تا MEKANIX واقعاً قابل انتشار Production باشد.

مبنای دسته‌بندی را هم روی اصول OWASP API Security گذاشتم؛ مخصوصاً کنترل دسترسی در سطح آبجکت، سطح فیلد و سطح Function که دقیقاً با مشکلات فعلی پروژه منطبق‌اند. ([OWASP API Security Top 10][1])

# 1. اول از همه: سیستم Authorization مرکزی

این مهم‌ترین تغییر پروژه است.

الان بعضی APIها `requireAuth` دارند، بعضی ندارند.

مثلاً:

```text
/api/profile
/api/prepay
```

از `requireAuth` استفاده می‌کنند، اما بسیاری از این‌ها نه:

```text
/api/vehicles
/api/jobs
/api/invoices
/api/messages
/api/notifications
/api/admin/*
/api/wallets
/api/reviews
/api/referral
/api/insurance
...
```

این نباید این‌طور باشد.

### باید یک سیستم مرکزی داشته باشیم:

```ts
requireAuth()
requireRole("ADMIN")
requireRole("TECHNICIAN")
requireRole("CUSTOMER")

requireOwnership()
requireJobParticipant()
requireVehicleOwner()
requireInvoiceAccess()
```

مثلاً:

```ts
const session = await requireAuth(req);

if (session instanceof NextResponse) {
  return session;
}
```

بعد:

```ts
requireRole(session, "ADMIN")
```

یا:

```ts
requireRole(session, ["ADMIN", "TECHNICIAN"])
```

اصل مهم این است که **Default باید Deny باشد**؛ یعنی API تا وقتی صراحتاً اجازه‌ای تعریف نشده، دسترسی ندهد. این دقیقاً با توصیه OWASP برای Function-Level Authorization منطبق است. ([OWASP API Security Top 10][2])

# 2. مالکیت Objectها باید کامل شود

این یکی از جدی‌ترین مشکلات فعلی است.

مثلاً الان API خودرو می‌تواند چیزی شبیه این دریافت کند:

```json
{
  "customerId": "customer_123"
}
```

اما:

> چرا Client باید بتواند تعیین کند این خودرو متعلق به چه کسی است؟

نباید.

باید از Session بفهمیم:

```text
session.userId
        ↓
Customer
        ↓
Vehicle
```

مثلاً:

```ts
const customer = await db.customer.findUnique({
  where: {
    userId: session.userId
  }
});
```

و بعد:

```ts
where: {
  id: vehicleId,
  customerId: customer.id
}
```

یعنی اگر کاربر ID خودرو شخص دیگری را بفرستد:

```text
403 Forbidden
```

نه اینکه خودرو را برگردانیم.

OWASP دقیقاً این مسئله را BOLA می‌نامد و تأکید می‌کند **هر endpointی که با ID به رکورد دسترسی دارد باید authorization همان object را بررسی کند.** ([OWASP API Security Top 10][1])

# 3. `userId / customerId / technicianId` نباید از Client قابل اعتماد باشند

در پروژه فعلی این الگو زیاد وجود دارد:

```json
{
  "userId": "...",
  "customerId": "...",
  "technicianId": "..."
}
```

این خطرناک است.

### قانون جدید:

#### برای Customer

هیچ‌وقت:

```ts

```

منبع حقیقت نباشد.

بلکه:

```ts

→ Customer
→ customer.id
```

#### برای Technician

همین:

```text
session.userId
→ Technician
→ technician.id
```

#### Admin

فقط Admin می‌تواند در صورت نیاز ID شخص دیگری را انتخاب کند.

# 7. Job Status باید State Machine واقعی داشته باشد

الان Client می‌تواند Status بفرستد:

```json
{
  "status": "COMPLETED"
}
```

ولی این کافی نیست.

باید انتقال وضعیت کنترل شود.

مثلاً:

```text
REQUESTED
 ↓
ACCEPTED
 ↓
EN_ROUTE
 ↓
ARRIVED
 ↓
DIAGNOSING
 ↓
WAITING_APPROVAL
 ↓
REPAIRING
 ↓
COMPLETED
```

نباید تکنسین بتواند:

```text
REQUESTED → COMPLETED
```

را مستقیم انجام دهد.

یا:

```text
CUSTOMER → COMPLETED
```

را تغییر دهد.

### Permission Matrix:

| Action           | Customer | Technician | Admin |
| ---------------- | -------: | ---------: | ----: |
| ACCEPT           |        ❌ |          ✅ |     ✅ |
| EN_ROUTE         |        ❌ |          ✅ |     ✅ |
| ARRIVED          |        ❌ |          ✅ |     ✅ |
| DIAGNOSING       |        ❌ |          ✅ |     ✅ |
| WAITING_APPROVAL |        ❌ |          ✅ |     ✅ |
| APPROVE_REPAIR   |        ✅ |          ❌ |     ✅ |
| REPAIRING        |        ❌ |          ✅ |     ✅ |
| COMPLETED        |        ❌ |      محدود |     ✅ |
| CANCEL           |    محدود |      محدود |     ✅ |

این باید در Backend enforce شود، نه UI.

# 99. در نهایت یک Security Boundary مشخص

```text
                ┌───────────────┐
                │    Browser    │
                └───────┬───────┘
                        │
                HTTPS / Secure
                        │
              ┌─────────▼─────────┐
              │ Next.js / API v1  │
              └─────────┬─────────┘
                        │
          ┌─────────────┼─────────────┐
          │             │             │
       Auth        Authorization   Validation
          │             │             │
          └─────────────┼─────────────┘
                        │
                 Business Rules
                        │
                ┌───────▼───────┐
                │  PostgreSQL   │
                └───────────────┘
                        │
              ┌─────────┼─────────┐
              │         │         │

         Rate / Cache
```

```text
Client
  ↓

  ↓
User Identity
```

# چیزی که من برای MEKANIX پیشنهاد می‌کنم

اگر قرار است این پروژه واقعاً محصول اصلی شود، **بهتر نیست این ۹۰ مورد را پراکنده و یکی‌یکی اصلاح کنیم.**

من آن را در **۵ فاز مهندسی** می‌برم:

### فاز 01 — Security Hardening

تمام:

* Auth
* Authorization
* Ownership
* Admin
* WebSocket
* API validation
* Secret
* Headers

### فاز 02 — Domain Integrity

تمام:

* Job State Machine
* Invoice
* Warranty
* VIP
* Cancellation
* Assignment
* Pricing
* Referral
* Review

### فاز 03 — Financial Core

بدون درگاه واقعی هم می‌شود:

* Wallet Ledger
* Decimal Money
* Transaction
* Commission
* Withdrawal
* Refund
* Audit

### فاز 04 — Production Infrastructure

* PostgreSQL
* Redis
* Queue
* Storage
* Backup
* Monitoring
* CI/CD
* Staging
* Health Checks

### فاز 05 — Security & QA Certification

تست تمام:

```text
Anonymous
Customer
Technician
Admin
```

روی **تمام Endpointها** + تست BOLA + تست Race Condition + تست Business Logic.

## یک نکته خیلی مهم

من بعد از بررسی Snapshot فعلی، **این پروژه را خراب یا بی‌ارزش نمی‌بینم**؛ برعکس، Foundation آن خیلی جلو رفته و حتی Worklog نشان می‌دهد بخش UI، RTL، SEO و Hybrid Glass/Solid به شکل قابل‌قبولی جلو رفته‌اند.

مشکل اصلی این است که الان پروژه در وضعیت:

> **High-fidelity product prototype + backend demo**

است، نه:

> **Production-grade platform**

و این دو مرحله را نباید با هم قاطی کنیم.

اگر این ۵ فاز را درست اجرا کنیم، بعد از آن می‌توانیم UI را بدون ترس از اینکه Backend دوباره مجبورمان کند Flowها را عوض کنیم، به همان سطح جهانی که برای MEKANIX می‌خواهی برسانیم.
